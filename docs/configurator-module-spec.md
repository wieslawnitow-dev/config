# ТЗ: универсальный конфигуратор кастомных изделий

## 1. Назначение

Модуль конфигуратора предназначен для сайтов-лидогенераторов, которые продают изделия, изготавливаемые по индивидуальным параметрам: площадь, периметр, погонные метры, количество, материалы, механизмы, монтаж и дополнительные услуги.

Первый тестовый продукт: москитные сетки.

Будущие ниши:

- москитные сетки;
- жалюзи;
- ролеты;
- ворота;
- маркизы;
- плиссе;
- другие изделия на заказ с расчетом по размерам.

## 2. Продуктовая модель поставки

Каждый проданный сайт должен быть независимой связкой.

```text
Client site
├─ отдельный домен
├─ отдельный статический Astro build
├─ отдельный Supabase project клиента
├─ отдельные таблицы клиента
├─ отдельные Edge Functions клиента
├─ отдельные ключи клиента
└─ отдельные настройки/история/заявки клиента
```

Не использовать централизованную базу для всех клиентов.

Требования:

- данные клиента не хранятся в общей базе продавца;
- клиент может сам поддерживать цены и настройки;
- сайт должен продолжать работать как статический сайт на обычном хостинге;
- точный расчет, заявки и история настроек работают через Supabase клиента;
- у продавца не должно быть постоянной необходимости иметь доступ к данным клиента;
- должна быть возможность восстановить продаваемую конфигурацию после ошибок клиента.

## 3. Общая архитектура

Стек:

- Astro SSG для статических SEO-страниц;
- React island для интерактивного конфигуратора;
- static HTML shell конфигуратора до загрузки React;
- Supabase клиента для закрытых данных, заявок и расчета;
- Supabase Edge Functions клиента для точной цены и валидации;
- конфиги продукта, страниц и публичных опций отделены от секретных цен и формул.

Основная схема:

```text
Astro static page
→ static configurator shell
→ React activation after first interaction
→ runtime config/version check
→ request to client Supabase Edge Function
→ closed calculation in client Supabase
→ return safe result to browser
```

На обычном хостинге лежит только публичная сборка:

```text
HTML
CSS
JS UI
SEO content
public labels/options
page context
```

Не должно попадать в публичную сборку:

```text
секретные формулы
закупочные цены
маржа
закрытые коэффициенты
service role key
CRM/webhook secrets
Supabase admin keys
```

## 4. Режимы расчета

Поддержать два режима, но для продаваемого продукта с секретной логикой основным считается `private_remote`.

```text
public_local
```

- расчет выполняется в браузере;
- подходит только для публичных цен и не секретных формул;
- быстрее и автономнее;
- не подходит, если формула или коэффициенты являются коммерческой тайной.

```text
private_remote
```

- браузер отправляет выбранные параметры в Edge Function;
- Edge Function читает закрытые таблицы Supabase клиента;
- формула и коэффициенты остаются закрытыми;
- браузер получает только безопасный результат;
- подходит для продаваемой версии по умолчанию.

Fallback при недоступности Supabase:

- не показывать выдуманную точную цену;
- показать сообщение о невозможности точного расчета;
- разрешить отправить заявку без цены или с пометкой `price_unavailable`;
- сохранить SEO-страницу полностью рабочей без расчета.

## 5. Supabase клиента

Для каждого сайта создается отдельный Supabase project.

Рекомендуемые сущности:

```text
sites
countries
cities
products
product_types
objects
options
compatibility_rules
public_config_matrix
price_components
service_rules
formula_rules
config_versions
schema_versions
leads
lead_events
rate_limit_events
```

Закрытые таблицы:

```text
price_components
service_rules
formula_rules
config_versions
schema_versions
leads
rate_limit_events
```

Публично допустимые данные:

```text
названия опций
публичные описания
публичные ограничения интерфейса
единицы измерения
валюта
страна/город обслуживания
готовая публичная матрица совместимости без цен
```

Безопасность:

- включить Row Level Security;
- frontend использует только anon key;
- расчет точной цены идет только через Edge Function;
- Edge Function использует server-side доступ;
- service role key никогда не попадает в браузер;
- все входящие параметры валидируются на стороне Edge Function;
- заявка не должна принимать произвольный HTML/JS без очистки;
- для публичных endpoints настроить rate limiting по IP;
- дополнительно ограничивать запросы по `site_id` и типу endpoint;
- `calculate-price` должен иметь throttling, чтобы защитить лимиты Supabase клиента;
- `submit-lead` должен иметь антиспам: honeypot, cooldown, captcha/hCaptcha при подозрительной активности;
- CORS должен быть ограничен доменами клиента;
- подозрительные запросы логируются без сохранения лишних персональных данных.

## 6. Версионирование и совместимость

Нужно исключить ситуацию, когда новый frontend работает со старой базой клиента или старая Edge Function получает новый формат заказа.

Версии:

```text
frontend_schema_version
config_schema_version
pricing_engine_version
supabase_schema_version
edge_function_version
public_matrix_version
```

Требования:

- версии записываются в статический build, Supabase config и Edge Functions;
- при активации конфигуратора выполняется легкая проверка совместимости;
- Edge Function обязана проверять версию входящего запроса;
- несовместимые версии не должны приводить к неправильной цене;
- при несовместимости показать безопасную ошибку и разрешить заявку без цены;
- baseline-конфигурация должна хранить версии, под которые она создана;
- миграции должны обновлять `supabase_schema_version` и при необходимости `config_schema_version`;
- изменение runtime config должно обновлять `public_matrix_version` или `public_matrix_hash`.

Поведение при конфликте версий:

```text
version mismatch
→ stop exact calculation
→ show update/configuration error
→ allow lead with price_unavailable
→ log version_mismatch event
```

## 7. Baseline и откат настроек

Нужна защита от поломки конфигурации клиентом.

Модель версий:

```text
config_versions
├─ id
├─ label
├─ type: baseline | client_edit | restore_point
├─ status: active | archived
├─ config_schema_version
├─ pricing_engine_version
├─ public_matrix_version
├─ config_json
├─ created_at
├─ created_by
└─ notes
```

Правила:

- `baseline` создается при передаче сайта клиенту;
- `baseline` нельзя редактировать через обычную админку;
- активная конфигурация создается как копия baseline;
- каждое сохранение клиента создает `client_edit` snapshot;
- перед крупным изменением можно создать `restore_point`;
- должна быть функция восстановления baseline;
- должна быть функция восстановления предыдущей версии;
- после отката расчет, совместимость и public matrix должны валидироваться;
- откат не должен удалять заявки, события и историю клиента.

Минимальные действия в админке:

```text
Сохранить изменения
Создать точку восстановления
Откатить к продаваемой версии
Откатить к предыдущей версии
Проверить конфигурацию
Проверить совместимость версий
Пересобрать публичную матрицу
```

## 8. Миграции и первичная установка

В репозитории должны быть артефакты для разворачивания сайта клиента:

```text
supabase/migrations/*
supabase/seed-baseline.sql или seed-baseline.json
supabase/functions/calculate-price
supabase/functions/submit-lead
supabase/functions/get-config-matrix
supabase/functions/rebuild-config-matrix
supabase/functions/restore-config
site/public-config
site/page-context
```

Требования:

- схема базы воспроизводима;
- baseline воспроизводим;
- функции разворачиваются отдельно для Supabase клиента;
- сайт подключается к Supabase клиента через публичные env-переменные;
- секреты функций хранятся в Supabase, а не в frontend;
- миграции версионируются и применяются последовательно;
- миграции не должны затирать `leads`, `lead_events`, `client_edit`, `restore_point` и активную клиентскую конфигурацию;
- destructive migration запрещена без backup/snapshot;
- после миграции выполняется проверка схемы, baseline, активной конфигурации и public matrix.

## 9. Build-time и runtime настройки

Разделить данные, которые требуют пересборки сайта, и данные, которые могут меняться в Supabase без rebuild.

```text
build-time config
```

- SEO-тексты;
- структура страниц;
- slug-и;
- title/description/H1;
- статический shell;
- публичный page context;
- статические блоки коммерческих страниц.

Изменение этих данных требует rebuild.

```text
runtime config
```

- цены;
- коэффициенты;
- правила формул;
- доступность опций;
- сервисные правила;
- совместимость;
- текущие настройки клиента;
- интеграции заявок.

Изменение этих данных не должно требовать rebuild, но должно обновлять предсобранную public config matrix.

Если клиенту разрешено менять публичные названия, SEO-тексты или структуру страниц через админку, должен быть отдельный rebuild webhook/process. По умолчанию клиент не должен свободно менять SEO-структуру без контролируемой пересборки.

## 10. Runtime config matrix

Чтобы UI не расходился с настройками Supabase, после активации конфигуратора React должен получить актуальную публичную матрицу конфигурации.

Endpoint:

```text
get-config-matrix
```

Назначение:

- вернуть актуальные публичные опции;
- вернуть совместимость без секретных цен;
- вернуть режимы `selectable/fixed/disabled`;
- вернуть публичные ограничения размеров;
- вернуть версии схем;
- не раскрывать формулы, маржу и закрытые коэффициенты.

Матрица не должна собираться тяжелым SQL-запросом при каждом открытии калькулятора.

Правильная модель:

```text
client changes config
→ validate config
→ precompute public_config_matrix_json
→ store matrix with version/hash
→ get-config-matrix returns ready JSON by one fast read
```

Требования к производительности:

- `get-config-matrix` должен отдавать готовый JSON из `public_config_matrix` или аналогичного cache/table;
- Edge Function не должна на каждый запрос заново парсить все сырые `compatibility_rules`;
- тяжелая сборка матрицы выполняется только при изменении runtime config, сохранении клиента, миграции или откате;
- у матрицы должен быть `public_matrix_version` или `public_matrix_hash`;
- ответ можно кэшировать с коротким TTL и инвалидировать при изменении версии;
- если матрица устарела или невалидна, точный расчет блокируется до пересборки/валидации.

Пример ответа:

```json
{
  "ok": true,
  "config_schema_version": "1.0.0",
  "pricing_engine_version": "1.0.0",
  "public_matrix_version": "42",
  "public_matrix_hash": "abc123",
  "options": {},
  "compatibility": {},
  "field_modes": {},
  "limits": {}
}
```

Модель работы:

```text
static shell
→ first interaction
→ load React
→ get-config-matrix
→ validate versions
→ hydrate current selection
→ calculate price when enough fields are selected
```

## 11. Размещение на страницах

Конфигуратор размещается на коммерческих страницах:

- главная;
- страницы цены;
- страницы видов изделий;
- страницы объектов установки;
- страницы монтажа;
- городские страницы;
- mono-location и multi-location версии сайтов.

Отдельная страница калькулятора не обязательна. Если создается, она может быть служебной и не индексироваться.

## 12. Performance-модель

Цель: не ухудшать скорость Astro-страниц.

Требования:

- страница загружается как обычная статическая Astro-страница;
- конфигуратор виден как статический HTML shell;
- React не запускается при первичной загрузке страницы;
- полная интерактивность включается после первого действия пользователя в блоке;
- shell и React-версия имеют одинаковую HTML/CSS-геометрию;
- место под превью, цену, подсказки и ошибки зарезервировано заранее;
- не использовать `client:load` для тяжелого конфигуратора на всех коммерческих страницах;
- предпочтительная модель: static shell + lazy/dynamic activation on first interaction;
- `get-config-matrix` и `calculate-price` выполняются только после взаимодействия пользователя;
- не выполнять тяжелые сетевые запросы к Supabase до взаимодействия пользователя.

Cold start / remote latency:

- UI должен показывать явное состояние расчета;
- запросы должны иметь timeout;
- при таймауте разрешить заявку без цены;
- можно выполнять warm-up, когда блок конфигуратора близко к viewport;
- на desktop можно дополнительно warm-up на `pointerenter`;
- на mobile warm-up должен работать через viewport/focus, а не только hover;
- warm-up не должен блокировать загрузку страницы и SEO-контент.

## 13. Контекст страницы

Контекст задается внутри страницы, а не через URL-параметры.

Пример:

```ts
pageContext = {
  product: 'mosquito_nets',
  city: 'kyiv',
  defaultObject: 'balcony_door',
  defaultType: 'dvernye',
  defaultMesh: 'antikoshka',
  defaultService: 'turnkey'
}
```

Контекст должен:

- предзаполнять shell и React-версию;
- ограничивать стартовые варианты;
- менять подсказки;
- менять стартовое превью;
- передаваться в запрос расчета;
- не менять SEO-теги после загрузки страницы.

Если сайт mono-location, переключение города может быть скрыто или зафиксировано. Если multi-location, город должен валидироваться через runtime config и Edge Function.

## 14. Модель заказа и сохранение состояния

Заказ может содержать несколько разных изделий одновременно.

```text
Order
├─ site_id
├─ country
├─ city
├─ currency
├─ locale
├─ service_mode
├─ urgency
├─ items[]
└─ customer
```

Пример:

```text
Позиция 1: окно, рамочная сетка, 800x1200, 3 шт
Позиция 2: балконная дверь, дверная сетка, 700x2100, 1 шт
Позиция 3: окно, антикошка, 900x1300, 1 шт
```

Глобальное состояние заказа должно сохраняться между статическими страницами сайта.

Требования:

- `items[]` не должны пропадать при переходе между коммерческими страницами;
- выбранные `city`, `service_mode`, `urgency` и текущий draft заказа сохраняются в браузере;
- данные формы контакта можно сохранять только ограниченно и с учетом приватности;
- для корзины предпочтителен `sessionStorage`;
- для города/единиц/предпочтений допустим `localStorage`;
- у сохраненного состояния должен быть TTL;
- при изменении `site_id`, домена, версии схемы или несовместимой матрицы старое состояние сбрасывается или мигрируется;
- не хранить чувствительные данные дольше необходимого;
- после успешной заявки очищать draft заказа или переводить его в submitted state.

Рекомендуемое разделение:

```text
sessionStorage
├─ items[]
├─ service_mode
├─ active_item_id
└─ draft_total_state

localStorage
├─ city preference
├─ unit preference
└─ non-sensitive UI preferences
```

## 16. Геометрия и расчетные модели

Модуль должен поддерживать несколько измерительных моделей.

```text
area_m2 = width_m * height_m
perimeter_m = 2 * (width_m + height_m)
linear_m = length_m * quantity
unit = fixed count
calculated_weight_kg = geometry/material based weight
```

Применение:

- `area_m2`: полотно, сетка, ламели, панели;
- `perimeter_m`: профиль, рамка, покраска, уплотнители;
- `linear_m`: направляющие, рельсы, карнизы, профили;
- `unit`: фурнитура, крепления, ручки, моторы, пульты;
- `calculated_weight_kg`: ворота, тяжелые полотна, подбор автоматики;
- `service`: замер, доставка, монтаж, демонтаж, сложность объекта.

Геометрию можно считать в браузере для UX и предварительной проверки, но точная цена в режиме `private_remote` считается только в Edge Function.

## 17. Формула цены

Формула должна быть модульной и храниться/исполняться так, чтобы в режиме `private_remote` она не раскрывалась в браузере.

Базовая логика позиции:

```text
item_price =
  area_m2 * material_price_m2
  + perimeter_m * profile_price_m
  + perimeter_m * paint_price_m
  + linear_m * linear_component_price_m
  + unit_components_price
  + mechanism_price
  + automation_price
  + mounting_hardware_price
```

После этого:

```text
position_price = max(item_price, min_item_price) * quantity
```

Сервисная часть:

```text
service_price =
  measure_price
  + delivery_price
  + installation_base
  + installation_by_product_type
  + installation_by_object_type
  + installation_by_complexity
  + dismantling_price
  + urgency_modifier
```

Итог:

```text
total = sum(position_price) + service_price
```

В браузер возвращать только безопасный результат:

```json
{
  "ok": true,
  "currency": "UAH",
  "total": 4200,
  "display": {
    "items": "3500",
    "service": "700",
    "delivery": "included"
  }
}
```

Не возвращать в браузер:

- формулу;
- закупочные цены;
- маржу;
- секретные коэффициенты;
- полные таблицы компонентов цены.

## 18. Валюта, налоги и округление

Расчет должен учитывать страну, валюту, локаль и правила отображения цены.

Поля:

```text
currency
locale
rounding_rule
tax_mode
price_display_mode
```

Примеры:

```text
UAH → округление до целых или до 10 UAH
PLN → округление до 1 PLN или 0.01 PLN
EUR → округление до 0.01 EUR
```

Налоги:

```text
tax_mode = included | excluded | reverse_charge | not_applicable
```

Отображение:

```text
price_display_mode = exact | range | from | unavailable
```

Edge Function должна возвращать уже нормализованную цену для отображения, а frontend не должен сам решать налоговую и валютную логику.

## 19. Отключаемые и фиксированные параметры

Каждое поле поддерживает режимы:

```text
selectable
fixed
disabled
```

`selectable`:

- пользователь видит поле;
- пользователь выбирает значение;
- значение участвует в расчете.

`fixed`:

- поле может быть скрыто или показано как фиксированное;
- значение задано конфигом;
- значение участвует в расчете.

`disabled`:

- поле скрыто;
- значение не участвует в расчете;
- параметр выбрасывается из формулы.

Финальная интерпретация этих режимов должна выполняться в Edge Function, чтобы клиентский UI не мог подменить расчет.

## 20. Совместимость опций

Форма показывает только доступные комбинации.

Примеры:

```text
mesh = antikoshka
→ доступны только типы изделий, которые поддерживают антикошку
```

```text
type = plisse
→ antikoshka скрыта, если плиссе не поддерживает такое полотно
```

Фильтрация работает в обе стороны:

- выбранное полотно фильтрует типы изделий;
- выбранный тип изделия фильтрует полотна;
- выбранный объект фильтрует типы изделий;
- выбранный механизм фильтрует автоматику;
- выбранный сервис фильтрует доступные условия монтажа/доставки.

Рекомендуемая модель:

```text
selected constraints
→ find valid configurations
→ show only option values present in valid configurations
```

В режиме `private_remote`:

- UI получает актуальную публичную совместимость через `get-config-matrix`;
- финальная проверка совместимости обязательна в Edge Function;
- несовместимый запрос не должен считаться, даже если пользователь изменил frontend.

## 21. Правила конфликтов выбора

Двусторонняя фильтрация должна иметь предсказуемое поведение.

Приоритеты:

```text
1. locked page context
2. последний явный выбор пользователя
3. обязательные требования продукта
4. recommended defaults
5. fallback defaults
```

Правила:

- locked page context нельзя автоматически сбрасывать;
- если новый выбор делает зависимое поле несовместимым, сбрасывается зависимое поле, а не последний выбор пользователя;
- если конфликтует несколько полей, сбрасывать минимальное число зависимых значений;
- после автосброса показать короткое уведомление;
- не сбрасывать всю форму без явной причины;
- повторный расчет выполнять только после валидного состояния.

Пример:

```text
Пользователь на странице antikoshka
→ mesh locked/recommended as antikoshka
→ type list показывает только совместимые типы
→ plisse не показывается или disabled с пояснением
```

## 22. Условная видимость полей

Поля показываются только если они релевантны текущей конфигурации.

Примеры:

```text
рамочная сетка на окно
→ automation скрыта
```

```text
рулонная сетка на террасу
→ automation доступна
```

```text
откатные ворота
→ automation доступна
→ construction_work доступна
```

Логика:

```text
field.visible = selected_configuration.supports(field)
```

## 23. Автоматика и управление

Автоматика должна быть универсальным модулем, не привязанным только к воротам.

```text
automation
├─ none
├─ manual
├─ motorized
├─ remote_control
├─ smart_home
├─ sensor_based
└─ timer_based
```

Применение:

- москитки: моторизованные рулонные системы, пульт, smart home;
- жалюзи/ролеты: электропривод, датчики солнца/ветра, smart home;
- ворота: привод, пульты, фотоэлементы, GSM/Wi-Fi, smart home.

## 24. Дополнительные модули для ворот

Если ворота планируются как важная ниша, заложить опциональные модули сразу.

```text

```

- секционные;
- откатные;
- распашные;
- рулонные;
- гаражные;
- промышленные.

```text
construction_work
```

- подготовка проема;
- бетонирование;

- направляющая;


- пульт;
- клавиатура;
- фотоэлементы;
- датчики;
- домофон;
- GSM/Wi-Fi модуль.


- ширина/высота проема;
- уклон;
- тип основания;
- наличие электричества;

Дополнительные расчетные параметры:

```text
calculated_weight_kg
wind_load_class
motor_power_class
panel_thickness
foundation_type
opening_width

```

Назначение:

- вес полотна влияет на подбор автоматики;
- ветровая нагрузка влияет на конструкцию и безопасность;
- толщина панели влияет на цену, вес и теплотехнические свойства;
- основание и проем влияют на монтаж и строительные работы.

## 25. Визуальное превью

Конфигуратор показывает небольшое, четкое, недетализированное превью изделия.

Превью меняется по параметрам:

```text

profile_color
fabric_or_mesh_type
mounting_type
mechanism
automation
```

Для первого этапа достаточно схематического CSS/SVG-превью без тяжелых изображений.

Требования:

- превью не ухудшает LCP;
- размеры области превью фиксированы;
- изменение превью не вызывает layout shift;
- превью передает интент конфигурации, а не является фотореалистичным.

## 27. Remote calculation UX states

UI должен явно поддерживать состояния удаленного расчета.

```text
idle
activating
loading_config
ready
calculating
calculated
validation_error
version_mismatch
rate_limited
remote_timeout
remote_unavailable
price_unavailable
submitted
```

Правила:

- пользователь не должен терять введенные данные при ошибке;
- при `calculating` показывать компактный loader в зоне цены;
- при `rate_limited` показать мягкое сообщение и предложить отправить заявку без точного расчета;
- при `remote_timeout` разрешить повторить расчет;
- при `remote_unavailable` разрешить отправить заявку без цены;
- при `version_mismatch` не считать цену и логировать событие;
- ошибки не должны менять высоту блока так, чтобы вызвать заметный CLS.

## 32. Acceptance criteria

Модуль считается готовым для MVP, если:

- конфигуратор виден на статической Astro-странице до загрузки React;
- React активируется только после взаимодействия пользователя;
- можно добавить несколько изделий в один заказ;
- корзина и draft заказа сохраняются между статическими страницами;
- есть режим `private_remote` через Supabase Edge Function клиента;
- есть `get-config-matrix` для runtime UI-конфигурации;
- `get-config-matrix` отдает предсобранную матрицу, а не строит ее тяжелым запросом на каждом вызове;
- публичные endpoints защищены rate limiting, CORS allowlist и server-side validation;
- секретная формула и закрытые коэффициенты не попадают в браузер;
- расчет учитывает площадь, периметр, погонные метры, штуки и опционально расчетный вес;
- цвет рамки может считаться через периметр и цену покраски за погонный метр;
- монтаж считается отдельно и зависит от изделия/объекта/сервиса;
- валюта, налоги и округление определяются в Edge Function;
- несовместимые параметры скрываются в UI;
- совместимость повторно проверяется в Edge Function;
- фильтрация работает в обе стороны;
- конфликты выбора решаются по описанным приоритетам;
- параметры могут быть selectable/fixed/disabled;
- превью меняется от выбора пользователя;
- UI поддерживает состояния удаленного расчета, rate limit и таймаутов;
- форма корректно работает на мобильном и десктопе;
- страница без JS остается читаемой и SEO-полезной;
- при недоступности Supabase можно отправить заявку без точной цены;
- у каждого клиента может быть отдельный Supabase project;
- baseline-конфигурация сохраняется отдельно и может быть восстановлена;
- изменения клиента сохраняются в history/snapshots;
- версии frontend/config/pricing/supabase/public matrix проверяются перед расчетом;
- миграции не затирают клиентские заявки и настройки;
- Lighthouse не показывает критичных просадок LCP/CLS/INP из-за модуля.
