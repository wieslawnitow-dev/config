# ТЗ: универсальный конфигуратор кастомных изделий

## 1. Назначение

Модуль конфигуратора предназначен для сайтов-лидогенераторов, которые продают изделия, изготавливаемые по индивидуальным параметрам: площадь, периметр, погонные метры, количество, материалы, механизмы, монтаж и дополнительные услуги.

Первый тестовый продукт: москитные сетки.

Будущие ниши:

- москитные сетки;
- жалюзи;
- ролеты;
- ворота;
- маркизы;
- плиссе;
- другие изделия на заказ с расчетом по размерам.

## 2. Продуктовая модель поставки

Каждый проданный сайт должен быть независимой связкой.

```text
Client site
├─ отдельный домен
├─ отдельный статический Astro build
├─ отдельный Supabase project клиента
├─ отдельные таблицы клиента
├─ отдельные Edge Functions клиента
├─ отдельные ключи клиента
└─ отдельные настройки/история/заявки клиента
```

Не использовать централизованную базу для всех клиентов.

Требования:

- данные клиента не хранятся в общей базе продавца;
- клиент может сам поддерживать цены и настройки;
- сайт должен продолжать работать как статический сайт на обычном хостинге;
- точный расчет, заявки и история настроек работают через Supabase клиента;
- у продавца не должно быть постоянной необходимости иметь доступ к данным клиента;
- должна быть возможность восстановить продаваемую конфигурацию после ошибок клиента.

## 3. Общая архитектура

Стек:

- Astro SSG для статических SEO-страниц;
- React island для интерактивного конфигуратора;
- static HTML shell конфигуратора до загрузки React;
- Supabase клиента для закрытых данных, заявок и расчета;
- Supabase Edge Functions клиента для точной цены и валидации;
- конфиги продукта, страниц и публичных опций отделены от секретных цен и формул.

Основная схема:

```text
Astro static page
→ static configurator shell
→ React activation after first interaction
→ request to client Supabase Edge Function
→ closed calculation in client Supabase
→ return safe result to browser
```

На обычном хостинге лежит только публичная сборка:

```text
HTML
CSS
JS UI
SEO content
public labels/options
page context
```

Не должно попадать в публичную сборку:

```text
секретные формулы
закупочные цены
маржа
закрытые коэффициенты
service role key
CRM/webhook secrets
Supabase admin keys
```

## 4. Режимы расчета

Поддержать два режима, но для продаваемого продукта с секретной логикой основным считается `private_remote`.

```text
public_local
```

- расчет выполняется в браузере;
- подходит только для публичных цен и не секретных формул;
- быстрее и автономнее;
- не подходит, если формула или коэффициенты являются коммерческой тайной.

```text
private_remote
```

- браузер отправляет выбранные параметры в Edge Function;
- Edge Function читает закрытые таблицы Supabase клиента;
- формула и коэффициенты остаются закрытыми;
- браузер получает только безопасный результат;
- подходит для продаваемой версии по умолчанию.

Fallback при недоступности Supabase:

- не показывать выдуманную точную цену;
- показать сообщение о невозможности точного расчета;
- разрешить отправить заявку без цены или с пометкой `price_unavailable`;
- сохранить SEO-страницу полностью рабочей без расчета.

## 5. Supabase клиента

Для каждого сайта создается отдельный Supabase project.

Рекомендуемые сущности:

```text
sites
countries
cities
products
product_types
objects
options
compatibility_rules
price_components
service_rules
formula_rules
config_versions
leads
lead_events
```

Закрытые таблицы:

```text
price_components
service_rules
formula_rules
config_versions
leads
```

Публично допустимые данные:

```text
названия опций
публичные описания
публичные ограничения интерфейса
единицы измерения
валюта
страна/город обслуживания
```

Безопасность:

- включить Row Level Security;
- frontend использует только anon key;
- расчет точной цены идет только через Edge Function;
- Edge Function использует server-side доступ;
- service role key никогда не попадает в браузер;
- все входящие параметры валидируются на стороне Edge Function;
- заявка не должна принимать произвольный HTML/JS без очистки.

## 6. Baseline и откат настроек

Нужна защита от поломки конфигурации клиентом.

Модель версий:

```text
config_versions
├─ id
├─ label
├─ type: baseline | client_edit | restore_point
├─ status: active | archived
├─ config_json
├─ created_at
├─ created_by
└─ notes
```

Правила:

- `baseline` создается при передаче сайта клиенту;
- `baseline` нельзя редактировать через обычную админку;
- активная конфигурация создается как копия baseline;
- каждое сохранение клиента создает `client_edit` snapshot;
- перед крупным изменением можно создать `restore_point`;
- должна быть функция восстановления baseline;
- должна быть функция восстановления предыдущей версии;
- после отката расчет и совместимость должны валидироваться.

Минимальные действия в админке:

```text
Сохранить изменения
Создать точку восстановления
Откатить к продаваемой версии
Откатить к предыдущей версии
Проверить конфигурацию
```

## 7. Миграции и первичная установка

В репозитории должны быть артефакты для разворачивания сайта клиента:

```text
supabase/schema.sql
supabase/seed-baseline.sql или seed-baseline.json
supabase/functions/calculate-price
supabase/functions/submit-lead
supabase/functions/restore-config
site/public-config
site/page-context
```

Требования:

- схема базы воспроизводима;
- baseline воспроизводим;
- функции разворачиваются отдельно для Supabase клиента;
- сайт подключается к Supabase клиента через публичные env-переменные;
- секреты функций хранятся в Supabase, а не в frontend;
- продавец может пересобрать сайт с продаваемыми параметрами без доступа к текущим данным клиента, если клиент предоставит только нужные публичные настройки или чистый baseline.

## 8. Размещение на страницах

Конфигуратор размещается на коммерческих страницах:

- главная;
- страницы цены;
- страницы видов изделий;
- страницы объектов установки;
- страницы монтажа;
- городские страницы;
- mono-location и multi-location версии сайтов.

Отдельная страница калькулятора не обязательна. Если создается, она может быть служебной и не индексироваться.

## 9. Performance-модель

Цель: не ухудшать скорость Astro-страниц.

Требования:

- страница загружается как обычная статическая Astro-страница;
- конфигуратор виден как статический HTML shell;
- React не запускается при первичной загрузке страницы;
- полная интерактивность включается после первого действия пользователя в блоке;
- shell и React-версия имеют одинаковую HTML/CSS-геометрию;
- место под превью, цену, подсказки и ошибки зарезервировано заранее;
- не использовать `client:load` для тяжелого конфигуратора на всех коммерческих страницах;
- предпочтительная модель: static shell + lazy/dynamic activation on first interaction;
- запрос точного расчета в Supabase выполняется только после достаточного выбора параметров;
- не выполнять сетевые запросы к Supabase до взаимодействия пользователя, кроме явно легких health/config запросов, если они нужны.

## 10. Контекст страницы

Контекст задается внутри страницы, а не через URL-параметры.

Пример:

```ts
pageContext = {
  product: 'mosquito_nets',
  city: 'kyiv',
  defaultObject: 'balcony_door',
  defaultType: 'dvernye',
  defaultMesh: 'antikoshka',
  defaultService: 'turnkey'
}
```

Контекст должен:

- предзаполнять shell и React-версию;
- ограничивать стартовые варианты;
- менять подсказки;
- менять стартовое превью;
- передаваться в запрос расчета;
- не менять SEO-теги после загрузки страницы.

## 11. Модель заказа

Заказ может содержать несколько разных изделий одновременно.

```text

├─ site_id
├─ country
├─ city
├─ currency
├─ service_mode
├─ urgency
├─ items[]
└─ customer
```

Пример:

```text

Позиция 2: балконная дверь, дверная сетка, 700x2100, 1 шт
Позиция 3: окно, антикошка, 900x1300, 1 шт
```

## 12. Модель позиции

```text
Item
├─ object_type
├─ product_type
├─ width
├─ height
├─ quantity
├─ profile_color
├─ fabric_or_mesh_type
├─ mounting_type
├─ mechanism
├─ automation
└─ optional_addons
```

Минимальный набор:

- объект установки;
- тип изделия;
- ширина;
- высота;
- количество;
- цвет профиля/рамки;
- тип полотна/материала;
- сервисный сценарий.

Расширенный набор:

- крепление;
- механизм;
- автоматика;
- срочность;
- доставка;
- замер;
- монтаж;
- демонтаж;
- комментарий;
- фото объекта.

Фото объекта не участвует в расчете на первом этапе, но может передаваться в заявку.

## 13. Геометрия и расчетные модели

Модуль должен поддерживать несколько измерительных моделей.

```text
area_m2 = width_m * height_m
perimeter_m = 2 * (width_m + height_m)
linear_m = length_m * quantity
unit = fixed count
```

Применение:

- `area_m2`: полотно, сетка, ламели, панели;
- `perimeter_m`: профиль, рамка, покраска, уплотнители;
- `linear_m`: направляющие, рельсы, карнизы, профили;
- `unit`: фурнитура, крепления, ручки, моторы, пульты;
- `service`: замер, доставка, монтаж, демонтаж, сложность объекта.

Геометрию можно считать в браузере для UX и предварительной проверки, но точная цена в режиме `private_remote` считается только в Edge Function.

## 14. Формула цены

Формула должна быть модульной и храниться/исполняться так, чтобы в режиме `private_remote` она не раскрывалась в браузере.

Базовая логика позиции:

```text
item_price =
  area_m2 * material_price_m2
  + perimeter_m * profile_price_m
  + perimeter_m * paint_price_m
  + linear_m * linear_component_price_m
  + unit_components_price
  + mechanism_price
  + automation_price
  + mounting_hardware_price
```

После этого:

```text
position_price = max(item_price, min_item_price) * quantity
```

Сервисная часть:

```text
service_price =
  measure_price
  + delivery_price
  + installation_base
  + installation_by_product_type
  + installation_by_object_type
  + installation_by_complexity
  + dismantling_price
  + urgency_modifier
```

Итог:

```text
total = sum(position_price) + service_price
```

В браузер возвращать только безопасный результат:

```json
{
  "ok": true,
  "currency": "UAH",
  "total": 4200,
  "display": {
    "items": "3500",
    "service": "700",
    "delivery": "included"
  }
}
```

Не возвращать в браузер:

- формулу;
- закупочные цены;
- маржу;
- секретные коэффициенты;
- полные таблицы компонентов цены.

## 15. Отключаемые и фиксированные параметры

Каждое поле поддерживает режимы:

```text
selectable
fixed
disabled
```

`selectable`:

- пользователь видит поле;
- пользователь выбирает значение;
- значение участвует в расчете.

`fixed`:

- поле может быть скрыто или показано как фиксированное;
- значение задано конфигом;
- значение участвует в расчете.

`disabled`:

- поле скрыто;
- значение не участвует в расчете;
- параметр выбрасывается из формулы.

Финальная интерпретация этих режимов должна выполняться в Edge Function, чтобы клиентский UI не мог подменить расчет.

## 16. Совместимость опций

Форма показывает только доступные комбинации.

Примеры:

```text
mesh = antikoshka
→ доступны только типы изделий, которые поддерживают антикошку
```

```text
type = plisse
→ antikoshka скрыта, если плиссе не поддерживает такое полотно
```

Фильтрация работает в обе стороны:

- выбранное полотно фильтрует типы изделий;
- выбранный тип изделия фильтрует полотна;
- выбранный объект фильтрует типы изделий;
- выбранный механизм фильтрует автоматику;
- выбранный сервис фильтрует доступные условия монтажа/доставки.

Рекомендуемая модель:

```text
selected constraints
→ find valid configurations
→ show only option values present in valid configurations
```

В режиме `private_remote`:

- базовую совместимость можно держать публично для скорости UI;
- финальная проверка совместимости обязательна в Edge Function;
- несовместимый запрос не должен считаться, даже если пользователь изменил frontend.

Если текущий выбор становится несовместимым, система должна:

- не ломаться;
- заменить значение на ближайшее допустимое;
- показать короткую подсказку пользователю.

## 17. Условная видимость полей

Поля показываются только если они релевантны текущей конфигурации.

Примеры:

```text
рамочная сетка на окно
→ automation скрыта
```

```text
рулонная сетка на террасу
→ automation доступна
```

```text
откатные ворота
→ automation доступна
→ construction_work доступна
```

Логика:

```text
field.visible = selected_configuration.supports(field)
```

## 18. Автоматика и управление

Автоматика должна быть универсальным модулем, не привязанным только к воротам.

```text
automation
├─ none
├─ manual
├─ motorized
├─ remote_control
├─ smart_home
├─ sensor_based
└─ timer_based
```

Применение:

- москитки: моторизованные рулонные системы, пульт, smart home;
- жалюзи/ролеты: электропривод, датчики солнца/ветра, smart home;
- ворота: привод, пульты, фотоэлементы, GSM/Wi-Fi, smart home.

## 19. Дополнительные модули для ворот

Если ворота планируются как важная ниша, заложить опциональные модули сразу.

```text
opening_type
```

- секционные;
- откатные;
- распашные;
- рулонные;
- гаражные;
- промышленные.

```text
construction_work
```

- подготовка проема;
- бетонирование;
- столбы;
- направляющая;
- демонтаж старых ворот.

```text
access_control
```

- пульт;
- клавиатура;
- фотоэлементы;
- датчики;
- домофон;
- GSM/Wi-Fi модуль.

```text
site_conditions
```

- ширина/высота проема;
- уклон;
- тип основания;
- наличие электричества;
- сложность подъезда.

## 20. Визуальное превью

Конфигуратор показывает небольшое, четкое, недетализированное превью изделия.

Превью меняется по параметрам:

```text
object_type
product_type
profile_color
fabric_or_mesh_type
mounting_type
mechanism
automation
```

Для первого этапа достаточно схематического CSS/SVG-превью без тяжелых изображений.

Требования:

- превью не ухудшает LCP;
- размеры области превью фиксированы;
- изменение превью не вызывает layout shift;
- превью передает интент конфигурации, а не является фотореалистичным.

## 22. Заявка

Форма заявки передает:

- site_id;
- страна;
- город;
- страница отправки;
- контекст страницы;
- все позиции заказа;
- рассчитанная цена или статус `price_unavailable`;
- выбранный сервис;
- имя;
- телефон;
- мессенджер;
- комментарий;
- прикрепленные фото, если есть.

Отправка заявки в продаваемой модели:

```text
frontend
→ submit-lead Edge Function клиента
→ leads table клиента
→ optional email/CRM/Telegram integration клиента
```

Интеграция должна быть заменяемой:

- Supabase leads table;
- PHP endpoint на хостинге;
- внешний form backend;
- webhook CRM;
- email gateway;
- Telegram gateway.

## 24. SEO-ограничения

Конфигуратор не должен:

- менять title, description, canonical, robots после загрузки;
- создавать индексируемые URL-параметры;
- генерировать дубли страниц;
- блокировать чтение основного контента без JS;
- ухудшать LCP/CLS/INP коммерческих страниц;
- требовать Supabase для отображения SEO-контента страницы.

Страница должна оставаться полноценной SEO-страницей без работающего JS и без доступного Supabase.


## 26. Acceptance criteria

Модуль считается готовым для MVP, если:

- конфигуратор виден на статической Astro-странице до загрузки React;
- React активируется только после взаимодействия пользователя;
- можно добавить несколько изделий в один заказ;
- есть режим `private_remote` через Supabase Edge Function клиента;
- секретная формула и закрытые коэффициенты не попадают в браузер;
- расчет учитывает площадь, периметр, погонные метры и штуки;
- цвет рамки может считаться через периметр и цену покраски за погонный метр;
- монтаж считается отдельно и зависит от изделия/объекта/сервиса;
- несовместимые параметры скрываются в UI;
- совместимость повторно проверяется в Edge Function;
- фильтрация работает в обе стороны;
- параметры могут быть selectable/fixed/disabled;
- превью меняется от выбора пользователя;
- форма корректно работает на мобильном и десктопе;
- страница без JS остается читаемой и SEO-полезной;
- при недоступности Supabase можно отправить заявку без точной цены;
- у каждого клиента может быть отдельный Supabase project;
- baseline-конфигурация сохраняется отдельно и может быть восстановлена;
- изменения клиента сохраняются в history/snapshots;
- Lighthouse не показывает критичных просадок LCP/CLS/INP из-за модуля.
